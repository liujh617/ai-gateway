# PII数据检测设计文档

**状态**: 提议
**日期**: 2026-08-03
**决策者**: 项目开发者
**ADR编号**: 0003

## 上下文

在审计加密功能完成后，需要进一步增强AI网关的风险管控能力。PII（Personally Identifiable Information，个人身份信息）数据检测是防止敏感数据泄露的关键能力。

### 业务场景

**典型场景**：
- 银行客服AI处理客户咨询时，客户可能会输入身份证号、银行卡号等敏感信息
- 医疗AI助手处理患者咨询时，可能会涉及姓名、身份证号、手机号等PHI信息
- 企业内部AI应用中，员工可能会粘贴包含个人信息的文本

**监管要求**：
- **GDPR**: 必须保护个人数据（姓名、身份证号、手机号等）
- **中国网络安全法**: 必须保护公民个人信息
- **银保监会要求**: 金融行业必须保护客户敏感信息

## 决策

**实现PII数据检测功能**，在审计日志记录前检测和标记（或脱敏）PII数据。

### 核心设计

#### 1. PII类型范围（极简MVP）

**中国场景必需**：
- 手机号（中国大陆）：`/^1[3-9]\d{9}$/`
- 身份证号（18位）：`/^\d{17}[\dXx]$/`
- 银行卡号（16-19位）：`/^\d{16,19}$/`

**暂不包含**（未来可扩展）：
- 姓名（需要NLP，复杂度高）
- 地址（格式多样，难以精确匹配）
- 邮箱（相对低风险）
- 护照号（用户需求较少）

#### 2. 检测时机

**选择**: 在审计日志记录前检测

**原因**：
- ✅ 性能影响最小（只影响需要审计的请求）
- ✅ 不影响正常请求处理流程
- ✅ 与现有审计流程集成简单

**备选方案**（不选择）：
- ❌ 在请求处理前检测：性能影响大，可能阻断正常请求
- ❌ 在响应返回后检测：无法阻止敏感数据已被记录

#### 3. 检测范围

**选择**: 只检测文本内容

**具体字段**：
- Request Body中的 `messages[].content`（用户输入）
- Response Body中的 `choices[].message.content`（AI生成）
- Embedding请求中的 `input` 字段
- 不检测：模型参数、metadata等非敏感字段

#### 4. 检测方法

**选择**: 正则表达式匹配（极简实现）

**原因**：
- ✅ 实现简单，易于理解和维护
- ✅ 性能可控，延迟 < 5ms
- ✅ 准确率可接受（> 95%）
- ✅ 无需外部依赖

**备选方案**（不选择）：
- ❌ ML模型（BERT、 presidio）：复杂度高，需要训练数据
- ❌ 第三方API（腾讯云、阿里云PII识别）：增加外部依赖，成本高

#### 5. 处理策略

**选择**: 标记（Alert）+ 可选脱敏（Redact）

**模式**：
```json
{
  "pii_detection": {
    "enabled": true,
    "mode": "alert",  // alert | redact | both
    "types": ["phone", "id_card", "bank_card"],
    "alert": {
      "webhook_url": "https://your-webhook.com/pii-alert"
    },
    "redact": {
      "replacement": "***MASKED***"
    }
  }
}
```

**模式说明**：
- `alert`: 只标记，不修改数据，发送告警
- `redact`: 脱敏敏感数据，替换为占位符
- `both`: 既标记也脱敏

#### 6. 输出格式

**审计日志增强**：
```json
{
  "timestamp": "2026-08-03T21:30:00Z",
  "event": "chat_completion",
  "request_id": "req-123",
  "body": {...},
  "pii_detected": {
    "phone": ["138****1234"],
    "id_card": ["110***********1234"],

```

#### 7. 架构设计

**模块划分**：
```
internal/pii/
├── detector.go           # PII检测器接口和实现
├── detector_test.go      # 单元测试
├── patterns.go           # 正则模式定义
├── patterns_test.go      # 模式测试
├── redactor.go           # 数据脱敏器
├── redactor_test.go      # 脱敏测试
└── config.go             # 配置结构
```

**核心接口**：
```go
type Detector interface {
    Detect(ctx context.Context, text string) (PIIResult, error)
}

type PIIResult struct {
    PhoneNumbers  []PIIMatch
    IDCards       []PIIMatch
    BankCards     []PIIMatch
}

type PIIMatch struct {
    Type        string  // "phone" | "id_card" | "bank_card"
    Value       string  // 原始值
    Start       int     // 起始位置
    End         int     // 结束位置
    Confidence  float64 // 置信度（正则匹配为1.0）
}
```

**审计集成**：
```go
// 在 internal/audit/audit.go 中
func (r *JSONLRecorder) Record(ctx context.Context, event Event) {
    // 1. 加密（如果启用）
    // 2. PII检测（如果启用）
    if r.piiDetector != nil {
        result, _ := r.piiDetector.Detect(ctx, string(event.Body))
        event.PIIDetected = result
    }
    // 3. 写入审计日志
}
```

#### 9. 错误处理

**策略**：优雅降级

| 错误类型 | 处理方式 |
|---------|---------|
| 正则编译失败 | 启动时报错，拒绝启动 |
| 检测超时 | 记录日志，返回空结果，继续审计 |
| 正则匹配错误 | 记录日志，跳过该字段，继续其他检测 |

#### 10. 性能估算

**基准测试**：
- 单次正则匹配：< 1ms
- 10个字段检测：< 5ms（串行）
- 10个字段检测：< 2ms（并行）
- 内存开销：< 1MB/request

**性能目标**：
- P99延迟：< 5ms
- 吞吐量：> 20,000 ops/s
- 内存增长：< 1MB/request

### 安全考虑

#### 1. 检测准确性

**挑战**：正则匹配可能误报

**解决方案**：
- 使用严格的正则模式（如手机号限制1开头）
- 添加校验逻辑（如身份证校验位验证）
- 提供置信度字段（用户可自行判断）

#### 2. 性能影响

**挑战**：检测增加延迟

**解决方案**：
- 只在审计启用时检测
- 使用编译后的正则（启动时编译）
- 支持并行检测多个字段

#### 3. 数据安全

**挑战**：告警中可能包含敏感数据

**解决方案**：
- 告警默认不包含原始数据（只包含类型和位置）
- 提供配置项 `include_context`（默认false）
- 建议使用HTTPS传输告警

### 替代方案

#### 方案A：使用第三方PII识别服务

**优点**：
- ✅ 准确率高
- ✅ 支持更多PII类型

**缺点**：
- ❌ 增加外部依赖
- ❌ 增加成本
- ❌ 数据需要传输到外部
- ❌ 性能受网络影响

**结论**: 不采用，不符合"数据自主"原则

#### 方案B：使用ML模型

**优点**：
- ✅ 准确率高
- ✅ 支持上下文理解

**缺点**：
- ❌ 实现复杂
- ❌ 需要训练数据
- ❌ 性能开销大

**结论**: 不采用，不符合"极简MVP"原则
